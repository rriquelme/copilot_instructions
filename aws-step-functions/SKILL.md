# aws-step-functions

A state machine that deploys but breaks at runtime is not done. This skill turns
"looks right" into "passes the linter and the AWS validator". Follow every step
in order. Do not skip the lint because the change was small.

Reference files in this folder (read the one you need before writing):

- `reference/jsonata-functions.md` — the **complete** list of JSONata functions
  and operators Step Functions accepts, the `$states` object, and a table of
  invented names with their real replacements. If a function is not listed, it
  does not exist.
- `reference/asl-rules.md` — fields allowed per state type, variable scoping,
  data flow, error names, Retry/Catch rules, integration ARNs.
- `reference/patterns.md` — linted, copy-safe snippets for the common shapes.

## Hard rules (apply while writing)

1. **JSONata everywhere.** New definitions: `"QueryLanguage": "JSONata"` at the
   top level. Never use `InputPath`, `OutputPath`, `Parameters`, `ResultPath`,
   `ResultSelector`, `Result`, `ItemsPath`, any `*Path` field, keys ending in
   `.$`, `Variable`/`StringEquals`-style Choice rules, or `States.*` intrinsic
   functions in a JSONata state. When modifying an existing JSONPath machine,
   keep JSONPath in the states you touch unless asked to convert.
2. **Only listed functions.** Before writing an expression with a `$name(`
   call, confirm `name` appears in `reference/jsonata-functions.md`. Not there:
   compose it from listed functions and operators, or say the transformation
   needs a Lambda. Never invent a function.
3. **Operators:** `=` not `==`, `and`/`or` not `&&`/`||`, `$not(x)` not `!x`,
   `&` for string concatenation, `??` for defaults.
4. **Every transition resolves.** Each `Next`, `Default`, rule `Next`, and
   `Catch.Next` names a state in the same `States` block. Every state except
   `StartAt` is the target of at least one transition. Every non-terminal
   state has exactly one of `Next` or `End: true`. `Choice`, `Succeed`, `Fail`
   have neither.
5. **Variables are definite.** A `$name` may be read only if an `Assign` on
   **every** path from `StartAt` to that state wrote it earlier. A variable
   assigned in state X is readable from X's successors, not in X's own
   `Output`/`Arguments`. Variables assigned inside a Map or Parallel body do not
   exist after it; pass data out through `Output`.
6. **`$states.result` only in `Output`/`Assign` of Task, Map, Parallel.**
   `$states.errorOutput` only inside `Catch`. Everywhere else the data is
   `$states.input` or a variable.
7. **No Pass state whose only job is to assign a variable** (except a
   `StartAt` Pass that captures execution input). Put the `Assign` on the state
   that produces the value, or in the matching Choice rule.
8. **Every Choice has a `Default`.** Every Task that can hang has
   `TimeoutSeconds`. Every `lambda:invoke` has the transient-error `Retry`
   from `reference/patterns.md` and `"Output": "{% $states.result.Payload %}"`
   (or reads `.Payload` in `Assign`).
9. **Guard optional input.** `$states.input.maybe ?? null`. An expression that
   yields nothing fails the execution.
10. **Types.** `Condition` is boolean, `Seconds`/`TimeoutSeconds`/
    `MaxConcurrency` are integers, DynamoDB attribute values are strings inside
    `{"S": ...}` / `{"N": ...}`. Convert with `$string()`, `$number()`,
    `$boolean()`.

## Procedure

### Step 0. Locate

Find the definition: a `.asl.json` file, or JSON embedded in Terraform
(`definition = jsonencode(...)`, `templatefile(...)`), CloudFormation/SAM
(`DefinitionString`, `DefinitionUri`, `Definition:`), CDK (`DefinitionBody`,
`StateMachine` construct), or Serverless Framework (`stepFunctions:`). Note the
effective `QueryLanguage`. If the definition is generated by code (CDK
constructs, Python/TypeScript builders) and no JSON exists, produce the JSON
with the project's synth/build command before linting; if no such command is
available, say so in the report and lint the closest JSON you can produce.

### Step 1. Plan on paper before touching JSON

Write this table in the reply (for a creation: all states; for a modification:
every state added, removed, or whose `Next`/`Assign`/`Output` changes):

| State | Type | Reads (input fields, `$vars`) | Writes (`Assign`) | Output | Next / on error |
|---|---|---|---|---|---|

Then check the table, not the JSON:

- Each `$var` in **Reads** appears in **Writes** of a state that is on every
  path before it.
- Each **Next / on error** target exists in the table (or already in the file).
- No state has an empty purpose ("Pass to set x" → move x to its predecessor).
- Terminal states are `Succeed`/`Fail` or carry `End: true`.

For a modification also list: states that transitioned to a removed/renamed
state, variables the removed states assigned and who still reads them.

### Step 2. Write

Use `reference/patterns.md` shapes. For each expression, look up every function
in `reference/jsonata-functions.md`. Keep expressions short; if one exceeds a
few lines, split into `Assign` steps on the states that produce the data.

### Step 3. Lint (mandatory)

```sh
python3 ~/.copilot/skills/aws-step-functions/scripts/lint_asl.py <path-to-definition>
```

Standard library only, Python 3.9+. Works on plain JSON and on files with an
embedded definition (Terraform heredoc/templatefile, CloudFormation YAML). Use
`-` to lint stdin. `--json` gives machine-readable output.

- Fix every `ERROR`, re-run until `0 error(s)`.
- Fix every `WARNING` or give a one-line reason it is intended.
- `INFO` lines are hints; act on `P001` (Lambda `Payload` output) unless the
  raw invoke response is wanted.
- The lint output of the final run goes in the reply verbatim, in a fenced block.
- If the run ends with `jsonata-python not installed`, expression syntax was
  not parsed. Install it once in the project's environment
  (`pip install jsonata-python`, or `uv add --dev jsonata-python`) and re-lint;
  if installing is not allowed, say so in the report.

Linter codes: `S0xx` structure (targets, orphans, Next/End, fields per type,
Retry/Catch shape), `J0xx` JSONata mode (forbidden JSONPath fields, `{% %}`
wrapping, unknown functions, bad operators, `$states.result` placement, syntax),
`V0xx` variables (never assigned, not on every path, wrong scope, shadowing,
Pass-only-assign), `P0xx` practice hints.

### Step 4. Validate with AWS (when the CLI and credentials are available)

```sh
aws stepfunctions validate-state-machine-definition \
  --definition file://<definition.json> --type STANDARD --severity WARNING
```

Expect `"result": "OK"` and an empty `diagnostics` list. Any diagnostic: fix,
re-lint, re-validate. Use `--type EXPRESS` for Express workflows. Quote the
output in the reply. If the CLI or credentials are missing, say "AWS validation
skipped: <reason>" in the report; do not claim it passed.

Optional but strong for expression-heavy states: test one state with a sample
input and variables.

```sh
aws stepfunctions test-state --definition file://<state-or-machine.json> \
  --state-name "<State name>" --input '{"orderId":"o-1","items":[{"sku":"a","qty":2}]}' \
  --variables '{"orderId":"o-1","attempt":0}' --inspection-level DEBUG \
  --role-arn <execution role arn>
```

`status` must be `SUCCEEDED` (or the intended `CAUGHT_ERROR`); `inspectionData`
shows `afterArguments`, `afterResultPath`, and resulting `variables`.

### Step 5. Report

Order: what changed (state list), final lint output (fenced), AWS validation
result or the reason it was skipped, anything unverified. Never say "should
work". If a rule above was deliberately broken on request, name the rule and
the request.

## Modification-specific checks

- Renaming a state: update every `Next`, `Default`, `Catch.Next`, and `StartAt`
  that named it. The linter catches misses (`S002`).
- Removing a state: its predecessors need a new target; its `Assign` variables
  must be assigned elsewhere or their readers removed (`V001`/`V002`).
- Inserting a state between A and B: A's `Next` → new state, new state's `Next`
  → B; the new state must not reference variables A assigns in the same turn
  unless A's `Assign` runs before (it does: A completes first).
- Adding a variable: assign it on **every** path that reaches its readers,
  including Catch paths and every Choice rule + Default.
- Moving logic into or out of a Map/Parallel: variables do not cross that
  boundary; pass values through `ItemSelector`/`Arguments` in and `Output` out.
- Converting a state from JSONPath to JSONata: set `"QueryLanguage": "JSONata"`
  on that state and replace every JSONPath field per `reference/asl-rules.md`.
  A machine that is JSONata at the top level cannot hold JSONPath states.

## Examples

**Request:** "add a step after PriceOrder that stores the total in DynamoDB"
**Right:** Table row for the new Task (reads `$orderId`, `$total`; writes
nothing; Next: whatever PriceOrder pointed to). Confirms `$total` is assigned in
PriceOrder's `Assign`; if not, adds `"total": "{% $states.result.Payload.total %}"`
there. Writes the Task with `"N": "{% $string($total) %}"`, `TimeoutSeconds`,
`Next`. Re-points PriceOrder's `Next`. Lints to 0 errors, runs the AWS
validator, quotes both.
**Wrong:** Adds a Pass state "SetTotal" with an `Assign`, then the DynamoDB
task with `"N": "{% $total %}"` (number, not string), forgets to re-point
`Next` so the new state is an orphan, reports "added the step".

**Request:** "make the choice also handle status = CANCELLED"
**Right:** Adds a rule `{ "Condition": "{% $status = 'CANCELLED' %}", "Next": "Cancelled" }`
before the Default, adds the `Cancelled` terminal state if missing, lints.
**Wrong:** Writes `"{% $status == 'CANCELLED' || $cancelled %}"` where
`$cancelled` is never assigned, and a `Next` to a state that does not exist.

**Request:** "compute the number of items in the Arguments"
**Right:** `"count": "{% $count($states.input.items) %}"`.
**Wrong:** `"count": "{% $length($states.input.items) %}"` (`$length` is for
strings; runtime `States.QueryEvaluationError`), or `$size(...)` (does not exist).
